## 2. 核心设计决策

### 2.1 为什么不复用 `HttpMappingInfo` 承载参数信息

`HttpMappingInfo` 在**每次全工程扫描**时构造，也出现在 gutter 渲染热路径上。参数签名提取需要遍历 `PsiParameter` + 读注解 + 解析类型，成本远高于现在只算 `qualifier`。

因此：**契约签名独立提取、独立缓存**，只在体检流程（后台、可取消）中计算。

```
HttpMappingInfo（不变，仅新增 pathTemplate 字段）
        │  qualifier
        ▼
ContractSignatureCache（PROJECT Service，key = qualifier + psiModificationCount）
        │
        ▼
ContractChecker → List<ContractIssue> → 报告面板 / Inspection / Markdown
```

### 2.2 配对索引复用现有倒排表

`BilateralMappingCacheService.SideSnapshot.byMatchUrl` 已经是 `Map<matchUrl, List<HttpMappingInfo>>`，体检只需要一个**只读快照**，不新建索引。

新增 API（唯一对既有 Service 的改动）：

```kotlin
/** 一次读取的双边只读快照，避免体检过程中反复进出 read action。 */
data class BilateralSnapshot(
    val clients: List<HttpMappingInfo>,
    val controllers: List<HttpMappingInfo>,
    val controllersByMatchUrl: Map<String, List<HttpMappingInfo>>,
    /** 每次 replace/upsert/remove 自增，用于判断报告是否过期。 */
    val version: Long,
)

fun snapshot(): BilateralSnapshot
```

`version` 用 `AtomicLong` 维护，`replaceClient` / `replaceController` / `upsert` / `removeByMethod` / `removeByClassQualifiedName` 各 `incrementAndGet()` 一次。报告面板据此判断「缓存已变，结果可能过期」。

### 2.3 路径模板：从 `matchUrl` 到可比较的段结构

现在 `PathBuilder.normalizeForMatch` 把 `{id}` 抹成 `{}`，丢失了变量名。体检需要原名，但**不能改 `matchUrl` 的语义**（配对逻辑依赖它）。

新增并列字段：

```kotlin
// HttpMappingInfo 新增
val pathTemplate: PathTemplate
```

```kotlin
// core/contract/PathTemplate.kt
data class PathTemplate(
    /** 形如 ["user", "{}"] 的段列表，路径变量段统一为 "{}" */
    val segments: List<String>,
    /** 按出现顺序的路径变量名，例如 ["id", "orderId"] */
    val variableNames: List<String>,
) {
    companion object {
        fun parse(url: String): PathTemplate
    }
}
```

`buildControllerUrl` / `buildClientUrl` 结果喂给 `PathTemplate.parse`，在 `HttpMappingInfo.create` 内一并算好（仍在 read action 内）。

### 2.4 规则模型

```kotlin
// core/contract/ContractRule.kt
enum class ContractSeverity { ERROR, WARNING, INFO }

/** 单条契约问题。所有 PSI 引用都是智能指针，可跨生命周期持有。 */
data class ContractIssue(
    val ruleId: String,
    val severity: ContractSeverity,
    /** 已本地化的用户文案 */
    val message: String,
    /** 问题锚点：通常是对端方法，用于双击跳转 */
    val anchors: List<SmartPsiElementPointer<PsiMethod>>,
    /** 修复建议，为空时只报告不修复 */
    val fixes: List<ContractFix> = emptyList(),
    /** 用于报告分组，例如 "PARAM_NAME" */
    val category: String = ruleId,
)

interface ContractRule {
    val id: String
    /** 在给定配对上下文上产出问题 */
    fun check(ctx: ContractCheckContext): List<ContractIssue>
}

class ContractCheckContext(
    val project: Project,
    val snapshot: BilateralSnapshot,
    val signatures: ContractSignatureProvider,
    val bundle: (key: String, vararg params: Any) -> String,
)
```

`ContractChecker` 负责：构建配对 → 逐规则执行 → 按 `(ruleId, 锚点)` 去重 → 排序（ERROR 在前，同级别按模块名）。

**规则失败必须隔离**：单条规则抛异常只记 warn 日志并跳过，不能影响整份报告（沿用 `EndpointScanner.recoverableScan` 的做法）。

### 2.5 规则清单与置信度（这是本版的核心内容）

| # | ruleId | 检查 | 严重级 | 置信度 | 误报控制 | 阶段 |
| --- | --- | --- | --- | --- | --- | --- |
| 1 | `orphan-client` | Feign 接口在工程内无任何 Controller 对端 | WARNING | 高 | 若工程内不存在任何 Controller 则整条规则跳过（纯客户端模块场景） | P0 |
| 2 | `param-name-mismatch` | 两端 `@RequestParam` **显式名**不同 | ERROR | 高 | 仅当两侧都从注解读到 name 才比较；任一侧回退到参数名 → 降为 INFO 或跳过 | P0 |
| 5a | `path-variable-missing` | URL 里有 `{x}`，方法参数中没有对应 `@PathVariable` | ERROR | 高 | 参数上无 `@PathVariable` 且无任何 `@PathVariable` 注解 → 跳过（可能是 `Map` 兜底） | P0 |
| 5b | ~~`path-variable-name-mismatch`~~ | ~~`{id}` 与 `@PathVariable("userId")` 显式名不同~~ | — | — | **已删除**：路径变量名只在各自一侧解析，跨侧不一致不会导致失败 | 不做 |
| 6 | `duplicate-mapping` | 两个 Controller 方法映射到同一 `matchUrl + method` | ERROR | 高 | `@RequestMapping` 未指定 method 的方法不参与；跨模块同路径视为嫌疑但降为 WARNING | P0 |
| 3 | `required-mismatch` | 客户端 `required=false`，服务端 `required=true` | WARNING | 中 | 两侧都显式声明时才比；`@RequestParam` 缺省视为 true 不参与 | P1 |
| 7 | `body-field-drift` | `@RequestBody` DTO 字段在两端不一致（缺字段 / 改名） | WARNING | 中 | 深度限制 2 层；`Map`/`Object`/`JsonNode` 一律跳过；只比字段名集合，不比嵌套结构 | P1 |
| 4 | `param-type-mismatch` | 查询参数类型不兼容 | INFO | 低 | **默认关闭**。HTTP 层字符串转换使大部分类型差异无害，误报率高 | P2 |
| 9 | `feign-name-unresolved` | `@FeignClient(name)` 对应不到服务地址 | — | 低 | **不做**。yml 结构千变万化（`spring.cloud.openfeign.client.config` / 注册中心 / `url` 直连），无法可靠判定 | 不做 |
| 8 | `response-type-mismatch` | 响应泛型结构不一致 | WARNING | 中 | 后移 1.2.1 | 不做 |

**误报率是本功能的生死线**：第一版宁可漏报。任何一条规则在 dogfood 中出现 > 5% 误报，直接下线而不是修文案。

### 2.6 幂等与性能预算

| 项 | 预算 |
| --- | --- |
| 500 端点首次全量体检 | ≤ 5s（后台、可取消） |
| 单文件 Inspection 增量 | ≤ 50ms（只查 O(1) 对端 + 2 条规则） |
| 内存 | 签名缓存 ≤ 2000 条 LRU |
| EDT 阻塞 | 0（全部在 `Dispatchers.Default` / `Task.Backgroundable`） |

#### D9 — Inspection

**新增**
- `inspection/ContractInspection.kt`（`: AbstractBaseUastLocalInspectionTool`）
- `inspection/ContractInspectionMessages.kt`（消息组装，与规则层共用）

**实现要点**

平台已有 `AbstractBaseUastLocalInspectionTool`，它**自带** `UastHintedVisitorAdapter` 与 `holder.registerProblem` 的装配，**不要自己写 `buildVisitor`**：

```kotlin
class ContractInspection : AbstractBaseUastLocalInspectionTool(UMethod::class.java) {

    override fun checkMethod(
        method: UMethod,
        manager: InspectionManager,
        isOnTheFly: Boolean,
    ): Array<ProblemDescriptor>? {
        val psiMethod = method.javaPsi as? PsiMethod ?: return null
        // 1. 从快照 O(1) 查对端；缓存为空直接 return null，绝不触发全量扫描
        // 2. 只跑 P0 规则
        // 3. manager.createProblemDescriptor(element, message, fixes, ProblemHighlightType.GENERIC_ERROR_OR_WARNING, isOnTheFly)
    }
}
```

- 描点元素用方法上的 REST 注解（与 gutter 一致，注解节点比方法节点稳定），而不是方法签名。
- `ProblemDescriptor` 通过 `manager.createProblemDescriptor(...)` 构造，QuickFix 作为第 3 个参数传入；**不要**用 `holder.registerProblem`（基类已经替你注册）。
- 缓存更新后调用 `DaemonCodeAnalyzer.getInstance(project).restart()`，让波浪线即时刷新（现有代码用的是 `settingsChanged()`，重启更彻底）。

**修改**
- `plugin.xml`：注册两次（`language="JAVA"` 与 `language="kotlin"`），`enabledByDefault=true`、`level=WARNING`、`groupBundle/groupKey` 归到 ApiHelper 组。

```xml
<localInspection language="JAVA"
                 shortName="ApiHelperContract"
                 bundle="messages.ApiHelperBundle"
                 key="inspection.contract.display.name"
                 groupBundle="messages.ApiHelperBundle"
                 groupKey="inspection.contract.group"
                 enabledByDefault="true"
                 level="WARNING"
                 implementationClass="com.lizhuolun.apihelper.inspection.ContractInspection"/>
```

- `core/contract/rules/BodyFieldDriftRule.kt`

**算法**：两侧 `BODY` 参数的 `PsiClass` 不同 → 取字段名集合 A、B →
- `A - B` → 「Feign 发送了 Controller 不认识的字段」（通常无害，INFO）
- `B - A` → 「Controller 期望但 Feign 未发送」（真实风险，WARNING）

**跳过条件**：任一侧类型无法解析为 `PsiClass`、是 `Map`/`Object`/`JsonNode`、字段数 > 100（防大 DTO 噪音）、类名以 `Map`/`Json` 结尾。

**验收**：`BodyFieldDriftRuleTest` 覆盖同名字段、改名、单向多字段、大 DTO 跳过。

## 7. 风险与回退

| 风险 | 概率 | 影响 | 应对 |
| --- | --- | --- | --- |
| 误报过多毁口碑 | 高 | 致命 | 规则置信度分级；dogfood 卡 5%；宁可漏报；`//noinspection` 可抑制 |
| 大工程体检超时 | 中 | 高 | 分块 + 可取消 + 签名缓存；>2000 端点时提示「仅检查当前模块」 |
| Kotlin UAST 与 Java PSI 差异 | 中 | 中 | 规则层只吃 `ContractSignature`，不碰 UAST；差异全关在提取器里 |
| 泛型 DTO 解析爆炸 | 中 | 中 | 深度 ≤ 2、字段 ≤ 100、无法解析即跳过 |
| 改 `HttpMappingInfo` 引发配对回归 | 低 | 高 | `pathTemplate` 是**新增字段**，`matchUrl` 语义不动；补 `HttpMappingInfoTest` |
| 3 周排期超支 | 中 | 中 | 硬切点：D10 未跑通面板 → 规则 7 移出；再超 → 反向调用方也移出 |

**回退开关**：Inspection 默认 `enabledByDefault=true`，但 Marketplace 发 EAP 时可临时改 `false`，面板保留——出问题不至于下架。
